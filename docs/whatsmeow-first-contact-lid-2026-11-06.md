# WhatsApp — first-contact LID resolution — November 6, 2026

## Diagnosis

Two new principal conversations on the Pocobusinecl and Note12businecl inboxes failed before sending with `Failed to send message: failed to resolve LID for PN …: USync returned no LID for …`. Both sessions were connected. Read-only registration queries through each affected session confirmed that both original phone numbers are registered and returned valid LIDs. No company message was sent by those queries.

The pinned Hypermeow dependency resolves a phone recipient through GetUserInfo before transmitting a message. An empty LID returns immediately, before message encryption/transmission. IsOnWhatsApp uses the interactive phone-registration lookup and returns the canonical recipient, including LIDs and the normalized phone identity. A valid Brazilian number may therefore be accepted by registration lookup while its originally typed PN fails the send path. Do not infer that these valid numbers need manual editing or remove a ninth digit by heuristic.

## Implementation

SendOnWhatsmeowService retains ConversationTargetResolver's authoritative contact_inbox.source_id. Only the exact missing-LID error for that phone permits one registration lookup of that same number. A registered result containing a distinct valid direct-recipient JID permits one send to that canonical recipient. An unchanged/missing/invalid/unregistered result fails. A second failure propagates. Transport errors, timeouts, 403 and errors naming another phone never enter recovery.

The outgoing payload is built once and reused with only `to` changed, preserving text/caption, exact attachment bytes, audio metadata, Pix, contacts and quoted content. No contact/source rewrite, alternate contact-phone guessing, bridge upgrade, migration, AI activation or customer-batch action is involved. The obsolete alternate-target loop was removed: the authoritative resolver supplies one target.
