# Thinking controls and rate-limit retries

The agent editor places **Pensamento / Thinking** directly after each provider/model selector, including the chat and vision reserve. Settings are independent per endpoint; route inversion moves both effort and retry policy with the selected model/connection/output budget. Legacy missing effort inherits the chat effort and is resolved to a level the endpoint supports. Existing stored profiles are not rewritten by deploying the feature.

`ReasoningPolicy` supplies documented levels to both `ModelCatalog` and `ProviderClient`. Qwen3.8 and GPT6Luna can disable reasoning with `none`; GPT-OSS20B/120B cannot. Models without configurable reasoning show an explicit notice and receive no invented parameter. Catalog APIs list model IDs but do not provide their supported effort enums, so those capabilities are maintained in the shared policy. Gemini2.5 maps levels to documented thinking budgets; default omits an explicit budget and Pro cannot disable thinking.

`retry_rate_limits` defaults to true independently for the primary and reserve of chat, vision and transcription. It is separate from `fallback.retry_primary`, which decides the starting endpoint of the **next** execution. Retrying a rejected generation does not change that policy.

Only HTTP429 with a valid provider delay can retry. Accept numeric or HTTP-date Retry-After; when absent, recognize Groq's “try again in19.2s” message. Round upwards and allow at most two retries with60seconds of total sleep **per endpoint/task**. Never shorten a longer provider delay. Unknown/invalid delays, other HTTP statuses, and exhausted budgets proceed to the configured reserve. Without a reserve, report the failure. This is a bounded wait inside the existing background generation path, not an increase in provider quota or a global per-organization scheduling system.

Each retry reuses the same messages/schema; transcription rewinds the same audio. Deliveries remain outside this provider loop, with the existing current-turn, permission, paused-state, approval and idempotency checks. A successful response is never retried because health persistence failed. No database migration is required.
